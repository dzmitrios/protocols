## Context

Репозиторий не содержит приложения. См. `proposal.md` — Why. Медиасервер — LiveKit, токен подписывает свой процесс на Express, браузер говорит с LiveKit напрямую.

Локальный LiveKit в режиме разработки слушает сигналинг на TCP 7880, ICE/TCP на 7881 и медиа на UDP 7882. Ключи режима разработки фиксированы: `devkey` / `secret`.

## Goals / Non-Goals

**Goals:**

- Два процесса в `LiveKit/`: Express выдаёт токен, React показывает комнату и панель соединения.
- Клиент использует Room API `livekit-client` и рисует состояние сам.
- Тип ICE читается из `getStats()` выбранной пары кандидатов каждого peer connection.
- Один `docker compose up` поднимает LiveKit рядом с приложением.

**Non-Goals:**

- Готовые компоненты `@livekit/components-react` и экран `AudioConference`.
- Учётные записи, проверка личности, список комнат на сервере.
- Деплой в AWS, LiveKit Cloud и свой TURN.
- Гарантия, что локальный запуск покажет `srflx` или `relay`. На одной машине выбранный кандидат обычно `host`.

## Decisions

### Каталог `LiveKit/` с двумя пакетами

- `LiveKit/server` — Express, один маршрут `POST /get-token`.
- `LiveKit/web` — Vite, React и TypeScript.
- `LiveKit/docker-compose.yml` — образ `livekit/livekit-server` с `--dev --bind 0.0.0.0` и пробросом 7880/tcp, 7881/tcp, 7882/udp.

Альтернатива — один пакет и LiveKit Cloud. Облако убирает порты и Docker, но прячет путь, ради которого затеян проект. Свой конфиг LiveKit вместо `--dev` нужен только когда появятся свои ключи и TURN.

### TypeScript в обоих пакетах

Оба пакета на TypeScript. Типы SDK показывают `Room`, состояние соединения, треки и грант токена в редакторе, что совпадает с учебной целью.

- `LiveKit/web` собирается Vite как приложение React на TypeScript.
- `LiveKit/server` пишет маршрут на TypeScript с типами Express. В разработке процесс запускается через `tsx`, отдельная сборка перед стартом не нужна.

Контракт комнат от языка не зависит. JavaScript убрал бы шаг проверки типов и подсказки по событиям LiveKit.

### Ответ токена содержит и JWT, и URL

`POST /get-token` принимает JSON `{ roomName, participantName }`. После `trim` пустое поле даёт 400 без токена. Успех — `{ token, url }`.

`url` берётся из `LIVEKIT_URL`. Для локального сервера это `ws://localhost:7880`. Ключи `LIVEKIT_API_KEY` и `LIVEKIT_API_SECRET` читаются только на сервере. В разработке допустимы значения `devkey` и `secret`, совпадающие с `--dev`.

Грант: `roomJoin`, комната из запроса, `canPublish`, `canSubscribe`. Поле `identity` — имя участника как есть. CORS разрешает origin Vite.

Альтернатива — зашить `ws://localhost:7880` в клиент. Тогда смена адреса требует правки фронтенда, а сервер уже и так единственное место с конфигурацией LiveKit.

### Свой UI на Room API

Экран входа собирает имя комнаты и имя участника. Кнопка входа — пользовательский жест для `getUserMedia`. Клиент запрашивает токен, создаёт `Room`, подключается по `url` и токену и включает микрофон.

Панель читает:

- состояние соединения: `connecting`, `connected`, `reconnecting`, `disconnected`;
- для publisher и subscriber peer connection — `candidateType` локального кандидата выбранной пары из `getStats()` (`host`, `srflx`, `relay`), иначе `unknown`;
- опубликован ли локальный микрофонный трек.

Список участников строится из локального участника и `remoteParticipants`. Говорящий отмечается флагом активности речи LiveKit. Заглушение не рвёт комнату: микрофон выключается и включается у локального участника. Выход вызывает `disconnect`.

Удалённое аудио вешается на `audio`-элементы по подписанным аудиотрекам.

Альтернатива — `@livekit/components-react` и `AudioConference`. Комната появилась бы быстрее, а выбранный ICE-кандидат и отдельные peer connection остались бы внутри библиотеки.

### Два peer connection в панели

`livekit-client` сейчас по умолчанию включает `singlePeerConnection`. Клиент создаёт `Room` с `singlePeerConnection: false`, чтобы панель показала отдельные соединения публикации и подписки. Если сервер не принимает двойной режим, SDK откатывается к одному соединению, и отсутствующая сторона остаётся `unknown`. Опрос `getStats()` идёт после подключения и при смене состояния, с небольшим интервалом, пока выбранная пара не появится.

Альтернатива — одна строка «тип ICE». Она врёт, когда publish и subscribe выбрали разных кандидатов, и плохо объясняет устройство LiveKit.

## Risks / Trade-offs

- [Локально виден в основном `host`] → Панель честно показывает `host`. `srflx` и `relay` остаются в контракте отображения, но не являются критерием локальной проверки. Их видно, когда кандидат выбран через STUN или TURN.
- [Две вкладки на одной машине дают эхо] → Проверка звука — наушники либо вторая машина. Это ограничение теста, не дефект сигналинга.
- [Отказ в микрофоне] → Вход в комнату сохраняется, панель показывает, что микрофон не опубликован, удалённое аудио продолжает играть.
- [Повторное имя участника] → Оба токена несут одну идентичность. Медиасервер оставляет в комнате одно подключение с этой идентичностью, список показывает одну строку.
- [UDP 7882 не проброшен] → Медиа не устанавливается, состояние может застрять в `connecting` или уйти в `reconnecting`. Compose публикует UDP явно.
- [Секреты `--dev` общеизвестны] → Они годятся только для локального сервера. В ответе токена секрета нет.

## Migration Plan

Новый каталог, переноса данных нет. Откат — не запускать Compose и процессы `LiveKit/server` и `LiveKit/web`.

Порядок первого запуска: `docker compose up` в `LiveKit/`, сервер токенов, Vite, две сессии браузера с одной комнатой и разными именами.
